# RTOS task table (block 0, fw 1.4)

Block 0 holds a table of 145 records at `0x4035fb66`: `u16 id` + 24-byte NUL-padded name, stride 26.
Names are looked up by task/object id, not by pointer, so Ghidra string xrefs find nothing. Search for the id constant instead.
Generated by `tools/rtos_tasks.py`. Relevant tasks: `0x13 FIRMUP_CLI`, `0x14 FIRMUP_SRV`, `0x53 FIRMUP_LED`, `0x1a LENS_FIRM_UP`, `0x24 PC_PTP`, `0x66 PTPCOM`, `0x67 PTPASYNC`, `0x7a WIFI_REMOCON_THROUGH`, `0x6d EYEFI`, `0x26 PC_USB`, `0x28 PC_USBSRV`.

## Task-CREATION table @ `0x7d9a9384` (2026-11-02) — func ptr / priority / stack per task

Separate from the id→name table above: a static **task-creation descriptor array** at runtime
`0x7d9a9384`, **134 records, stride 28 (0x1c) bytes**. Fields: `+0 u32 task id`, `+12 u32 entry fn
ptr`, `+16 u32 priority`, `+20 u32 stack size` (`+4/+8/+24` zero). Record ids run `0x01..0x86`
sequentially — i.e. this table spawns 134 of the 145 named tasks (omits id `0x00 DBG_OUT` and the
CPU0/bridge tasks `0x87..0x90`, which are brought up by a different path). The two tables share one id
space, so joining them gives the full registry (entry address + priority + stack for every named
task). Found via the single pointer xref to `FIRMUP_SRV`'s scanner `0x7de57532` landing in this array;
the table base itself appears as **no 32-bit immediate** in block 0 — the init loop reaches it via a
base register / small-data anchor (or from code in block 1/2, not disassembled), so the exact spawn
loop is not pinned statically. Reproduce the join with `python3 -I` over `blk00_40300000.bin` (base
`0x7d991020`): walk 28-byte records from `0x7d9a9384`, read id/+12/+16/+20, and index the name table
at file offset `0x5fb66`.

**`0x7de57532` = `FIRMUP_SRV` — confirmed by two independent tables** (name table id 0x14 ↔ creation
table id 0x14). So the SD-card `DCOLYMP` body-firmware scanner (`docs/firmware/camera-fw-update.md`)
is a standalone, statically-registered RTOS task spawned at kernel init — not code gated behind the
rec/menu app UI. `FIRMUP_CLI` (0x13) is its client half; `FIRMUP_LED` (0x53) drives the update LED.
The giant stacks (CA_MAIN 0x9000, REC_MAIN 0x3700) corroborate the id-space alignment.
